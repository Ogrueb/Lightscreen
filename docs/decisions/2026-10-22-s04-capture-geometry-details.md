# 2026-10-22 (Stage 6, S04): capture and area selection work in native pixels, mapped through the window's own ratio

**Decision.** `grabDesktop` builds one canvas in native desktop pixels; the area dialog covers that same native area and maps its own coordinates to it with the dialog window's single device pixel ratio. This replaces the plan's wording for S04 ("`AreaDialog` covers the virtual geometry in logical coordinates ... `resultRect` maps the logical selection to device pixels per screen"), which does not match how Qt 6 maps a window's coordinates.

**Why.** In Qt 6 a screen's logical geometry keeps its native top left corner and divides only its size by its ratio (`QScreen::geometry()`), so screens at different ratios leave gaps or overlaps in logical space. A window, however, has one ratio: Qt maps its widget coordinates to native pixels as `origin + (logical - origin) * ratio`, around the top left of the screen at the window's top left (or the window's screen when no screen is there), even where the window extends onto a screen with another ratio. Qt's own `QWindow::mapToGlobal` notes the same gap problem. Mouse positions inside the dialog are therefore a uniform scaling of native pixels, not `QScreen::geometry()` coordinates, and a per-screen mapping of the selection would put any part on a second screen in the wrong place. With the dialog covering the native area exactly and the canvas drawn at the dialog's ratio, one pixel of the canvas is one native pixel on every screen, and the selection maps back with that one ratio.

**Details.**
- `tools/capturegeometry.{h,cpp}` (new, pure functions, no `QScreen`): `deviceRect`, `deviceUnion`, `screenAt`, `logicalToDevice` (a global logical point through the screen that contains it, for the cursor), `dominantScreen` (largest native overlap, as Windows assigns a window's DPI), `windowGeometry` (the logical geometry a window on a given screen needs to cover a native rectangle, rounded outward), `selectionToDevice` (near edges rounded down, far edges up, clipped to the pixmap).
- `grabDesktop` grabs each screen with `QScreen::grabWindow(0)`, takes the native size from the grab (logical size times ratio can be one pixel off: 1707 x 1.5 = 2560.5), paints the grabs on a black canvas the size of their native union, draws the cursor at its native position at 1:1, and sets the canvas ratio to that of the screen holding most of it (for previews). `Screenshot::deviceGeometry()` gives where the canvas lies on the native desktop. If every grab is null the pixmap stays null, as before.
- `AreaDialog` takes that rectangle as an optional third constructor argument (`LightscreenWindow::selectArea` passes it; the tests leave it out). `showEvent` puts the dialog on the screen whose top left is the canvas's top left (else the dominant screen) with `setScreen` and `setGeometry(windowGeometry(...))`. `paintEvent` sets the pixmap's ratio to `devicePixelRatioF()` before drawing, so if Windows moves the window to another screen's DPI the mapping follows. `resultRect` and the magnifier use the pixmap's ratio, so the tests that set a ratio on an unshown dialog still check the mapping. `options.currentMonitor` is no longer read by the dialog: the canvas already covers only that screen.
- `os::grabWindow` (Windows) compares the window with the virtual desktop (`SM_XVIRTUALSCREEN` etc.) instead of `GetDesktopWindow()`, which is the primary monitor only. Everything there is physical pixels already.
- New source files carry the GPL v2 notice without a copyright-holder line; the line for the fork's own code is chosen with M16 (see `2026-10-15-m14-no-license-header-on-tests.md`).

**Rejected.**
- Per-screen mapping of a logical selection (the plan's wording): wrong for the reason above.
- One area dialog window per screen, each at its own ratio: exact by construction, but a selection across two monitors (a QA item) would need the selection shared between windows; a larger rewrite of a dialog the plan keeps.
- `QRectF::toAlignedRect()` for the selection: the same result for normalized rectangles, but it normalizes, which would change the recorded "not normalized" row for no gain.

**Risk.** Whether Windows keeps a spanning frameless window at its creation DPI is only checked by hand (`docs/windows-qa/2026-10-22-mixed-dpi-capture.md`). Xvfb cannot give Qt two screens (Qt's xcb backend reads RandR outputs, not Xinerama, and Xvfb has one output), so the cloud runs covered one screen at fractional ratios only.
